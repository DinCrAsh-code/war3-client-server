# Правила ИИ-агентов

Область действия: весь репозиторий `war3-client-server`, любой ИИ-агент
независимо от модели и инструмента. Это проектные правила, не личная
инструкция владельца и не копия правил другого продукта.

## Назначение и обязательные ограничения

Проект переводит Warcraft III от lockstep к авторитетной клиент-серверной
архитектуре. Главная цель — не передавать игроку запрещённое скрытое состояние.
Равноправные критерии качества: сохранить механику Warcraft, старые кастомные
карты и обычный режим игры. Удалять совместимость ради удобства реализации
или передавать полный мир ради совместимости нельзя.

Не объявлять целевую архитектуру готовой. Исследовательский успех одной
функции, карты или цепочки не доказывает полный матч и производительность.

**Прежняя архитектурная схема не принята за основу.** Не превращать
«оригинальный Game.dll на сервере», «симуляция клиента выключена» и
«локальный JASS повторяется для каждого игрока» в требования реализации.
Архитектура строится заново из целей, реальных зависимостей и экспериментов.

## Перед началом работы

1. Прочитать [README](README.md), [архитектуру](docs/ARCHITECTURE.md),
   [план](docs/ROADMAP.md) и относящийся к задаче контракт.
2. Прочитать канонический локальный handoff `.codex/PROJECT_STATE.md`, если
   он доступен. Отсутствие локального файла не мешает работать по публичным
   документам. Не создавать второй конкурирующий журнал состояния.
3. Проверить `git status --short --branch`, ветку, remotes и расхождение
   с upstream, если он существует. Не считать чужие изменения своими.
4. Для реверса прочитать [индекс](research/reverse/INDEX.md) и
   [классификацию](research/reverse/README.md); сначала искать существующую находку.
5. Сформулировать ожидаемый результат и способ его проверки. Не вводить
   зависимости, слои или публичные API без конкретной задачи.

## Границы документов и реализации

- `docs/` хранит требования, архитектуру, совместимость и критерии приёмки.
- `docs/decisions/` хранит ADR с явным статусом; предложение не равно решению.
- `research/reverse/` хранит сведения о движке, их классификацию и происхождение.
  Не превращать его в альтернативную реализацию продукта.
- `docs/archive/` сохраняет историю; не использовать её как текущий контракт.
- Профили точных сборок, сетевые схемы и внутренние layouts — разные контракты.
  Не смешивать адреса процесса с сетевыми ID или форматом записи действий.
- Здесь не импортируются код, продуктовые слои и история других приложений.
  Из исследований переносится только необходимое знание о движке со ссылкой
  на источник и пределами применимости.
- Не добавлять в Git игровые DLL/EXE, карты, реплеи, MPQ, дампы, декомпиляцию,
  базы дизассемблеров, секреты, личные пути или сырые приватные отчёты.
  Собственные минимальные тестовые исходники допустимы с ясным происхождением.

## Стандарт реверс-находок

Каждая находка получает стабильный `FND-NNNN`, один основной subsystem,
тип результата, уровень evidence и статус проверки в этом проекте.
Классификаторы и шаблоны определены в [правилах реверса](research/reverse/README.md).
ID не переиспользовать; новую находку и строку индекса менять одним коммитом.

Сохранять build scope, источник/ревизию, положительный и отрицательный
контроль, отвергнутые гипотезы и открытые границы. Адрес без точного образа
не является переносимым контрактом. Не превращать неподтверждённый offset
или результат одного опыта в молчаливый runtime fallback.

Чтение чужого отчёта отмечать как `source-reviewed`; `reproduced` допустим
только после собственного воспроизведения с указанным результатом.
Новые эксперименты не подразумеваются задачей на документацию.

## Единые правила веток и коммитов

Ветка: `codex/<scope>-<short-topic>`, например `codex/visibility-policy`.
Обычная работа интегрируется в `main` через PR. Инициализация пустого
репозитория — отдельная операция; правила не предписывают автоматический
push, публикацию или создание фиктивного начального коммита.

Все агенты используют один формат Conventional Commits:

```text
<type>(<scope>): <краткое действие>

Context: <проблема и причина изменения>
Changes: <что изменилось и что это даёт>
Validation: <фактические проверки и результат; либо not run — причина>
```

- `type`: `docs`, `feat`, `fix`, `refactor`, `test`, `perf`, `build`, `ci`,
  `chore`, `revert`. Новая база знаний реверса — `docs`, не готовая `feat`.
- `scope`: `project`, `agents`, `architecture`, `compatibility`, `validation`,
  `reverse`, `startup`, `simulation`, `jass`, `visibility`, `presentation`,
  `resources`, `maps`, `protocol`, `client`, `server`, `platform`, `build`, `ci`.
- Scope обязателен. Один логический результат на коммит. Заголовок до
  72 символов, без завершающей точки; язык описания — русский или английский,
  последовательно внутри одного коммита. Ключи шаблона остаются английскими.
- Для изменяющего контракт коммита указать `Compatibility:` и `Security:`
  с влиянием на карты/обычный режим и на выдачу скрытых данных соответственно.
- Для реверса добавить `Findings: FND-…`, `Evidence: <источник/ревизия>` и
  `Limits: <что не доказано>`. В публичном сообщении нет приватных путей.
- Несовместимый контракт обозначать `!` перед двоеточием и пояснять в теле
  `BREAKING CHANGE:`. Это обозначение не разрешает ломать карты и не заменяет
  согласование существенного изменения архитектуры.
- Не выдумывать результаты тестов, авторов или `Co-authored-by`.
  Использовать настроенную Git-идентичность; не подменять её ради коммита.
- Запрещены бессодержательные сообщения `update`, `fix stuff`, `wip`.

Примеры заголовков:

```text
docs(project): define client-server goals and compatibility
docs(visibility): classify fog findings and evidence limits
fix(protocol): reject stale object generations
test(compatibility): cover local camera script behavior
```

Перед коммитом просмотреть diff, выполнить нужные проверки и
`git diff --check`. Добавлять в index явные пути, затем проверить
`git diff --cached` и `git diff --cached --check`. Не использовать `git add .`
для смешанной рабочей копии. Не коммитить постороннюю работу.

Не делать force push, переписывание опубликованной истории, удаление чужих
веток/изменений и замену существующего remote без явного основания в задаче.
Создание документов само по себе не означает публикацию в удалённый репозиторий.

## Проверки и завершение

Для Markdown: ссылки, согласованность навигации/индекса/статусов, отсутствие
постороннего продуктового контекста, секретов и неподтверждённых обещаний.
Для изменения поведения: соответствующие сценарии из
[плана приёмки](docs/VALIDATION.md), включая отрицательные контроли.
Недоступные проверки перечислять; не обозначать их зелёными.

Описание PR: проблема и новое поведение, значимые решения, фактическая
проверка, влияние на совместимость и защиту информации, оставшиеся ограничения.
Заголовок PR использует тот же формат, чтобы squash-коммит сохранял стандарт.

В конце существенной работы обновить существующий локальный handoff,
сохранив его исключение из Git. Указать пользователю достигнутый результат,
проверки, ограничения и состояние коммита/push без догадок.
