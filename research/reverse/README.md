# Реверс движка: классифицированная база знаний

Назначение — хранить проверяемые сведения об устройстве Warcraft III,
не смешивая их с проектированием продукта. Вход: [индекс находок](INDEX.md).
Происхождение текущей базы: [источники и ревизии](SOURCES.md).
Для работы с реконструкцией коллеги: [карта src и приоритеты](SRC_MAP.md),
[полный каталог файлов](catalog/README.md). Каталог даёт навигацию;
FND-карточки фиксируют выводы и уровень их проверки.

## Структура

```text
research/reverse/
  INDEX.md                         быстрый поиск по подсистемам и статусам
  SOURCES.md                       источники, ревизии и границы переноса
  SRC_MAP.md                       приоритетные цепочки в реконструкции
  catalog/                         инвентарь всех исходников с Git blob
  tools/catalog_src.py              обновление инвентаря из commit
  findings/<subsystem>/FND-NNNN-*.md одна находка или связный контракт
  experiments/EXP-NNNN-*.md         отчёты будущих собственных экспериментов
  templates/FINDING.md              шаблон находки
  templates/EXPERIMENT.md           шаблон плана и результата опыта
```

`experiments/` создаётся вместе с первым реальным отчётом. Датированные
отчёты не заменяют индекс по подсистемам. Сырые игровые данные, дампы и
бинарники хранятся вне этого репозитория; здесь — выводы и воспроизводимость.

## Классификация по подсистеме

| Код каталога | Содержание |
|---|---|
| `startup` | Инициализация, владельцы контекстов, сессия, headless-граница, завершение |
| `simulation` | Объекты, команды, выделение, время, RNG, таймеры, бой, pathfinding |
| `jass` | VM, нативы, config/main, handles, события, локальные контексты |
| `visibility` | Туман, обзор, альянсы, невидимость/детект, право на сведения |
| `presentation` | Рендер, UI, камера, звук, эффекты, поля клиентского представления |
| `resources` | MPQ, данные карты, таблицы объектов, terrain/pathing, загрузка ресурсов |
| `network` | Оригинальный транспорт, сессии, ввод и запись; границы нового адаптера |
| `map-extensions` | Особенности конкретных карт и нативных расширений |

Выбирать один основной subsystem по владельцу контракта; пересечения
отражать тегами и ссылками. Каталог создаётся с первой находкой. Например,
приказы принадлежат `simulation`, хотя приходят через сеть. Общий roadmap
или предложение нового протокола находится в `docs`, а не в реверсе.

## Независимые признаки карточки

| Поле | Допустимые значения и смысл |
|---|---|
| `kind` | `contract` — наблюдаемое поведение; `boundary` — граница/зависимость; `negative-result` — опровергнутое предположение; `hypothesis` — проверяемое предположение |
| `evidence` | `unverified`, `static`, `isolated`, `connected` |
| `verification` | `source-reviewed` — проверено изложение источника; `reproduced` — опыт повторён в этом проекте; `not-tested` — проверки нет |
| `state` | `open`, `bounded`, `contradicted`, `superseded` |
| `scope` | Точная сборка, входы, среда и предел покрытия; обязательно текстом |
| `impact` | `security`, `compatibility`, `correctness`, `performance`, `operations`; можно несколько |

`static` устанавливает связь по коду, `isolated` — поведение ограниченного
компонента, `connected` — исполнение указанной цепочки с проверкой эффекта.
Это не проценты готовности. `bounded` значит, что есть результат в описанных
границах, а не что закрыта вся подсистема. Повторная проверка документа не
повышает evidence до `connected` и verification до `reproduced`.

Для реконструкции `static`/`source-reviewed` означает чтение опубликованного
тела; это не независимое доказательство его соответствия оригиналу. Форму
реализации отмечать для конкретного символа: C++-тело, asm-тело, redirect в
оригинал, декларация, регистрация. Ни комментарий `MATCH`, ни ключевое слово
`naked`, ни наличие `.cpp` не определяют полноту всей цепочки. P0/P1/P2 в
карте исходников задают порядок исследования и не заменяют поля карточки.

Если в карточке есть и статическая связь, и динамический результат, основной
уровень относится только к сформулированному выводу; различия указать в тексте.
Не распространять доказанность одного блока на соседние утверждения.

## Как добавить или изменить находку

1. Найти owning subsystem и проверить [INDEX](INDEX.md) на существующий контракт.
2. Использовать [шаблон находки](templates/FINDING.md), назначить следующий
   свободный `FND-NNNN`; ID глобален, неизменяем и не используется повторно.
3. Написать один точный вывод, источник и build scope; отделить результат от
   гипотез. Указать отрицательный контроль либо честно отметить его отсутствие.
4. Добавить строку индекса, связи с соседними находками и следующий вопрос.
5. Если результат меняет продуктовый контракт — обновить соответствующий
   документ или предложить ADR. Не менять архитектуру одним ярлыком находки.
6. Для эксперимента использовать [шаблон](templates/EXPERIMENT.md), хранить
   фактический исход, включая неудачи, и ссылаться на него из карточки.

Новые знания о старой находке обновляют её и индекс вместе. Опровергнутые
выводы сохраняются с `contradicted`; заменённые — с `superseded` и ссылкой.
Точные адреса допускаются только с типом координаты (RVA/VA), fingerprint
образа, методом установления и границами применимости; случайный адрес нельзя
копировать в runtime. Текущие карточки адресов и сырого кода не содержат.
