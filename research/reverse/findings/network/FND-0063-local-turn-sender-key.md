## Вывод

На показанном локальном пути `CNetData` берёт индекс активной записи `+0x610`, её локальный slot byte `record+0x2DC` и переводит его через таблицу участников `record+0x290` в participant key `entry+0x18`. Этот key сериализуется первым байтом вложенного turn subrecord, перед длиной и action payload. Полученный event type `0x1F` ставится в общую очередь с ненулевым record selector; при дальнейшем разборе turn тот же key может быть разрешён в sender ([FND-0060](FND-0060-sender-key-enrollment-boundary.md), [FND-0051](../jass/FND-0051-resume-sender-resolution.md)).

Условие маршрута существенно: [`0x6F54D930`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54D930.json) ведёт к этой сборке при session tag `LOOP` либо `NONE`; для прочих tags он выбирает отдельный flush/virtual send path. Поэтому здесь не доказаны байты реального online packet и тем более связь key с аутентифицированным peer. Наблюдаемая пара slot→key→sender есть локальная маршрутизация по таблице, а не credential check.

## Адресный маршрут и контроли

1. [`0x6F553470`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F553470.json) сначала дренирует queued events через `0x6F5530D0`, затем при `self+0x278>=4` вызывает `0x6F54D930`. Последняя функция при tag `0x4C4F4F50` (`LOOP`) или `0x4E4F4E45` (`NONE`) переходит в [`0x6F54D760`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54D760.json). При иных tags она вызывает [`0x6F650480`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F650480.json) для flush и далее `vtable+0x1C` на объекте `self+0x1C78`. Это отрицательный контроль: сетевой send branch **не проходит** через `0x6F54D760` в данном вызове; его собственный serializer требует отдельной проверки.
2. `0x6F54D760` выбирает active index `self+0x610` и выходит до сборки при положительном `record+0x2EC`, ненулевом guard `self+0xFD4`/`+0x13D0` (по индексу `0/1`) или отсутствии новых байтов относительно `self+0x2244`. Успешный путь берёт `record+0x2DC` и вызывает [`0x6F53E080`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53E080.json) на `record+0x290`. [S10 layout](../../../../src/Net/netdata.h) называет `+0x2DC` локальным слотом, `+0x290` таблицей участников. В `0x6F53E080` slot `0xFE` возвращает `0xFF` без lookup; иначе [`0x6F53E050`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53E050.json) находит participant в массиве обычных/observer slots, и функция возвращает `entry+0x18` или `0` при miss. Это два отрицательных контроля для предположения «каждый локальный слот даёт зарегистрированный key»; дальнейшую интерпретацию key `0`/`0xFF` нельзя выводить из одного writer.
3. `0x6F54D760` кладёт полученный key в первый byte временного subrecord, затем длину новых данных и сами данные. [`0x6F6522D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F6522D0.json) сериализует именно byte, word length, payload; это положительный контроль формата. `0x6F54D760` передаёт готовый store как event type `0x1F` через [`0x6F54CC10`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54CC10.json) с третьим аргументом `2` → [`0x6F54CAD0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54CAD0.json) → [`0x6F54C490`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54C490.json). Последняя пишет `event+0x15=2`; [`0x6F5491B0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5491B0.json) → [`0x6F548FF0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F548FF0.json) включает event в очередь. S10 [enqueue](../../../../src/Net/netevent_replaystream_records.cpp) реконструирует часть маршрута, однако его комментарий «все known callers передают trailing zero=0» не покрывает показанный S11 caller с аргументом `2`; этот комментарий не использован как доказательство значения поля.
4. При последующем вызове queue pump [`0x6F5530D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5530D0.json) передаёт event в [`0x6F551D80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551D80.json), где ненулевой `event+0x15` выбирает текущую активную запись `+0x610`. Type `0x1F` идёт через [`0x6F5516E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5516E0.json) к [`0x6F550730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550730.json), который читает byte sender-key из subrecord и ищет его в таблице этой записи. Это статический маршрут self-queued turn; поскольку pump в `0x6F553470` вызван **до** `0x6F54D930`, нет доказательства обработки нового event в том же вызове pump. Доставка при исполнении здесь не воспроизведена.

## Ограничения и отвергнутые гипотезы

Прочитаны S11 `raw_asm` и S10 без запуска DLL или byte-match; статусы `0x6F553470`/`0x6F548FF0` — `THUNK`, `0x6F54D930`/`0x6F54D760`/`0x6F53E080`/`0x6F6522D0` — `TODO`, `0x6F54CC10`/`0x6F54CAD0` — `DIFFERS`. Fingerprint предполагаемой сборки не установлен. Условия полей `+0x2EC`, `+0xFD4/+0x13D0`, `+0x2244` названы как guards по коду, без полного бизнес-смысла. Не доказаны штатная частота этого loopback пути, outcome при ключе `0`/`0xFF`, синхронная доставка каждого event и влияние replay. Самое существенное: **online branch** `0x6F54D930` минует данный serializer; по этой карточке нельзя выводить формат raw socket packet, сетевую admission policy или криптографическую/сессионную привязку peer к key.

## Значение для проекта

Оригинальный local slot и turn sender-key — разные координаты, связанные таблицей участников выбранной записи. При проектировании авторитетного входа этот alias нельзя использовать вместо проверки `connection → session → player`: она остаётся отдельным обязательным контрактом. Следующий адресный шаг — проследить `vtable+0x1C` online branch, источник его буфера и raw receiver до `0x6F54CAD0`; минимальный динамический контроль сравнит `LOOP` и сетевой tag при одинаковом локальном action, записав event selector, serialized key, полученный sender и реальный peer handle.
