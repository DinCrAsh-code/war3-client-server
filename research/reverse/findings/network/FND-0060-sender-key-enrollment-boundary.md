## Вывод

В S11 participant key, по которому позднее разрешается `sender` команд `ResumeTriggerExec` (`0x62`) и `TriggerSyncReady` (`0x63`), вносится в hash table **выбранной сетевой записи** при обработке событий `GameCreate`, `GameJoin` и `PlayerJoin`. У `PlayerJoin` это первый байт payload события; после проверки длины event builder вызывает hook, который передаёт этот байт в `0x6F551A80`. Вставка создаёт запись с этим key, а отдельный путь позже присваивает ей player ID в `entry+0x36`. Входной turn subrecord содержит свой байт key; lookup в той же таблице возвращает `entry+0x36` либо `0xFF` при отсутствии записи. Неизвестный key не доходит до trigger observer по показанному пути.

Это **локальное происхождение и разрешение key**, а не доказательство его привязки к аутентифицированному сетевому peer. `0x6F551D80` получает уже поставленный в очередь event; один из показанных источников той же очереди — replay stream. Непрерывного маршрута от конкретного raw socket packet/connection через session admission к байту key в корпусе здесь не установлено. Приравнивать event key к identity отправителя либо объявлять отсутствие внешней проверки нельзя.

## Адресный маршрут и контроли

1. [`0x6F54C490`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54C490.json) выделяет queued event и, если `id<0xFF`, `size<0xFFFFF` и `size2<0xFFFFF`, заполняет `event+0x08` payload pointer, `+0x0C/+0x10` lengths, `+0x14` event type и `+0x15` record selector; иначе освобождает event. [`0x6F54CAD0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54CAD0.json) — один caller; [S10 event enqueue](../../../../src/Net/netevent_replaystream_records.cpp) реконструирует поля. Это контроль формы event и границы размера, но в этих функциях нет connection/peer identity. [`0x6F54EB00`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54EB00.json) тоже вызывает `0x6F54CAD0` из replay stream, включая чтение record type `0x16`. Это отрицательный контроль гипотезы, что один факт наличия queued event уже означает живой вход от peer.
2. [`0x6F5530D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5530D0.json) берёт узел очереди `self+0xF38` и передаёт его в [`0x6F551D80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551D80.json). Последняя функция оборачивает `event+0x08/+0x0C` в reader, читает type из `+0x14` и выбирает record index: при `event+0x15==0` индекс `0`, иначе `SNetSessionInfo+0x610`. [S10 queue pump](../../../../src/Net/pausecallchainthunks.cpp) и [S10 event dispatcher](../../../../src/Net/netevent_dispatch.cpp) дают сверку. `+0x15` — selector записи, **не** sender-key из turn subrecord; это два разных байта на разных уровнях разбора.
3. В `0x6F551D80` event types `0x10/0x15/0x16` строят соответственно `CNetEventGameCreate`, `CNetEventGameJoin`, `CNetEventPlayerJoin` через [`0x6F54A0C0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54A0C0.json), [`0x6F5468A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5468A0.json) и [`0x6F5469E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5469E0.json), передавая hooks [`0x6F551B80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551B80.json), [`0x6F551C20`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551C20.json) и [`0x6F551CB0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551CB0.json). Builders сначала вызывают payload reader и виртуальную проверку выхода за длину; при её отказе hook не вызывается. При успехе они публикуют event observer lists и затем вызывают соответствующий hook. [S10 event builders](../../../../src/Net/netevent_dispatch.cpp) подтверждают этот порядок. Он ограничивает **разбор payload**, но не раскрывает проверку peer до помещения event в очередь.
4. [`0x6F652780`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F652780.json) читает первый байт type-`0x16` payload в `CNetEventPlayerJoin+0x14` ([S10 reader/layout](../../../../src/Net/netdata_replayrecordreaders.cpp)). Hook `0x6F551CB0` передаёт этот байт как key в [`0x6F551A80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551A80.json) на таблице `self + recordIndex*0x304 + 0x290`. Hooks GameCreate/GameJoin также берут byte `event+0x18` из своих parsed records и зовут `0x6F551A80`, но их полные payload semantics здесь не восстановлены. В `0x6F551A80` [`0x6F5518A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5518A0.json) присоединяет запись к таблице; запись получает key в `entry+0x18` и предварительный byte `entry+0x36=(key-1)|0x80`. Позднее [`0x6F5491D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5491D0.json) может заменить `+0x36` на player ID ([FND-0051](../jass/FND-0051-resume-sender-resolution.md)). Сам `0x6F551A80` не получает параметр peer/connection; неизвестны права источника event и поведение повторного key в полном lifecycle.
5. На входном turn [`0x6F550730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550730.json) reader [`0x6F652300`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F652300.json) берёт уже **другой** байт key из subrecord. Адрес таблицы снова `self + recordIndex*0x304 + 0x290`; [`0x6F54E7E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54E7E0.json) через [`0x6F54E7C0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54E7C0.json) → [`0x6F54C870`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54C870.json) сравнивает key и возвращает `entry+0x36` либо `0xFF` при miss. Затем для record `0` применяется player/action gate [`0x6F545270`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F545270.json); record `!=0` его обходит. Cases `0x62/0x63` передают полученный sender в соответствующие builders, а `FireCommand` пропускает observer delivery при `sender==0xFF`. Подробные условия gate и trigger-local проверки — [FND-0051](../jass/FND-0051-resume-sender-resolution.md), [FND-0053](../jass/FND-0053-trigger-ready-membership-boundary.md). Это положительный контроль совпадения enrollment lookup и turn lookup по выбранной таблице и отрицательный контроль неизвестного key.

## Ограничения и отвергнутые гипотезы

Не доказано, какой конкретный socket packet или peer создал `GameCreate`/`GameJoin`/`PlayerJoin` event, кто уполномочил первый byte key, и как network admission связывает connection с выбранным record index. Видимый raw W3GS listener [`0x6F6637C0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F6637C0.json) разбирает `0xF7` packet, но его показанный type dispatcher [`0x6F663700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F663700.json) охватывает LAN game-list types `0x2F..0x33` ([S10](../../../../src/Net/w3gs_typedispatch.cpp)); это **не** мост к queued turn/action `0x62/0x63`. Другой raw transport path может существовать. Показанный replay caller `0x6F54EB00` прямо исключает вывод «каждая запись таблицы соответствует живому peer» из одного факта обработки event. Это не доказательство обхода авторизации или уязвимости в оригинальной игре.

Статусы S11 смешанные (`EXACT`, `DIFFERS`, `TODO`); данные прочитаны по `raw_asm`, но не воспроизведены в DLL и не сверены с fingerprint образа. Изученные функции не устанавливают отсутствие иных admission checks, защиту от дубликатов key, поведение in-flight turn при выходе игрока и фактический record index для `0x62/0x63` в матче. Удаление участника и null lookup уже ограниченно разобраны в FND-0051; здесь дополнено только первоначальное заполнение таблицы и граница его происхождения.

## Значение для проекта

В авторитетном сервере `participant key` нельзя автоматически считать доказательством личности клиента: проверяемая связка должна иметь отдельные `connection → session/record → participant key → player ID` и затем `player ID → право на trigger/epoch`. Следующий адресный шаг — найти producer queued event до `0x6F54CAD0` для live turn и его связь с connection record; затем двухpeerовый опыт с различными keys, неизвестным/отозванным key и replay source покажет, где именно проходит admission. Пока этот мост открыт, FND-0060 ограничивает знание о старом движке, а не задаёт готовый wire-протокол.
