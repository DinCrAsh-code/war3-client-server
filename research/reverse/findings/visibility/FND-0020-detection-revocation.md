## Вывод

Для пути `CBuffSharedVision` смена получателя `old → new` — не простая
перезапись индекса. `0x6F0D5200` при различающихся индексах сначала
вызывает `0x6F28DC80` для `old`, затем `0x6F2967F0` для `new` на блоке
по `unit+0x13C`, после чего вызывает базовый `0x6F0D5190`. Базовый путь
при отличии сохранённого индекса `+0xCC` от `new` снимает эффект через
`0x6F284A50`, добавляет через `0x6F296680` на другом блоке по
`unit+0x130` и записывает `new` в `+0xCC`.
Параметр маски каналов берётся из `+0xD0`. При отдельном снятии
`0x6F0D36F0` вызывает базовое снятие `0x6F0D27B0`, затем снятие
блока `unit+0x13C` через `0x6F28DC80`. Таким образом, у этого эффекта
статически прослеживаются два слоя отзыва в разных handle-ref блоках.

`0x6F28DC80` после `0x6F27A400` вызывает пересчёт
`0x6F284DA0`; добавление `0x6F2967F0` делает то же после
`0x6F27A3C0`. Пересчёт берёт исходную маску юнита `+0x148` из
[`0x6F27A460`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F27A460.json): она включает слово `+0x24` разрешённого блока
`unit+0x13C` и, при отдельном флаге юнита, ещё один
источник от способности. Поле `unit+0x14C` сначала получает эту маску,
потом для каждого установленного в `+0x148` бита игрока `0..11`
добавляет его relation-поля `+0x88` и `+0xC8`. Это один проход по исходной
маске, без транзитивного расширения. В более позднем проходе
[`0x6F40A8F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F40A8F0.json)
`unit+0x14C` OR-ится в маску обновления юнита; назначение следующего
вызова `0x6F409E00` требует отдельного разбора.

## Контроли и пределы

Положительный статический контроль: при `old != new` в
`0x6F0D5200` порядок снятия и добавления в блоке `unit+0x13C` виден до
вызова `0x6F0D5190`; при отдельном снятии `0x6F0D36F0` оба слоя
вызываются последовательно. `0x6F284DA0` перезаписывает оба поля
`+0x148/+0x14C` перед OR отношений, поэтому штатно выполненный пересчёт
может удалить ранее попавший в них бит после отзыва источника.

Отрицательные контроли: при `old == new` `0x6F0D5200` пропускает
перенос блока `unit+0x13C`, а `0x6F0D5190` — перенос блока `unit+0x130`;
если в `+0x148` нет бита игрока `i`, его relation-поля не входят в
`+0x14C` через этот цикл. `0x6F27A400` сам по себе не проверяет
положительность счётчика перед декрементом: неверно парный вызов мог бы
его увести ниже нуля, но достижимость такого вызова из штатного жизненного
цикла не установлена.

Не следует выводить битовое слово блока `unit+0x13C` только из счётчика:
[`0x6F27A430`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F27A430.json)
имеет отдельный путь прямой установки бита `+0x24`, а снимает его лишь
при нулевом соответствующем счётчике. Не доказаны все источники этого
пути, полное назначение `+0x14C`, момент обновления при смене альянса,
фактическая публикация полей юнита, отсутствие утечки после отзыва и
эквивалентность опубликованного C++ оригинальной DLL. В S11 add/remove
и смена адресата имеют `TODO`, `0x6F284DA0` — `DIFFERS`.

Это продолжение [FND-0012](FND-0012-detection-refcounts.md) о счётчиках
и [FND-0014](FND-0014-submit-detection-gate.md) о раннем gate. Их блок
`unit+0x130` нельзя отождествлять с блоком `unit+0x13C` из этой цепочки.
Оно не даёт основания приравнять `IsUnitDetected`, маску `+0x14C`,
результат `SubmitUnit` и окончательное право клиента на сведения.
Следующий опыт: на двух игроках применить эффект к `A`, перенести его на
`B`, затем снять; на каждом шаге проверить счётчики и слова обоих блоков,
`unit+0x148/+0x14C`, JASS-запросы, `SubmitUnit` и локальный UI.
Контрольному игроку не давать обзор; отдельно проверить два перекрывающихся
источника и порядок их снятия.
