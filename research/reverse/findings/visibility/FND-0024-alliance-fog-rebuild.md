## Вывод

В S11 есть связный путь изменения направленных отношений двух игроков к
пересчёту fog-таблицы. Callback `0x6F43E960` берёт индексы игроков из
байтов входа `+0x15/+0x18` и набор флагов из `+0x1C`. Для допустимого
индекса второго игрока (`<16`) он выбирает `EnableAllianceFlag`
`0x6F3E6890` либо `DisableAllianceFlag` `0x6F3E69E0` для отдельных
типов `0..8` (тип `9` пропущен), затем вызывает
`CPlayerWar3FinishLeaveNotify` `0x6F41B4C0` для записи второго игрока.
Ветви по дополнительному флагу мира и сравнению двух записей игроков
ограничивают, какие типы вообще меняются; этот callback не равен
произвольному вызову `JASS_SetPlayerAlliance`.

Если у записи второго игрока указатель `+0x34` ненулевой, callback позже
берёт **другой** указатель из глобальной таблицы игроков `+0x34`, обновляет
его мировые маски через `0x6F408070`, ставит бит `2` в `fogTable+0x24`,
запускает `0x6F40A8F0(fogTable)` и затем проходит локальный UI-маршрут.
Тождество двух указателей из разных объектов не доказано.
В rebuild функция снимает этот бит после проходов. По IDA-телам её
последовательность такова:

1. Собрать для 16 игроков OR направленных полей relation-agent `+0x88`
   и `+0xC8` во временный массив.
2. **Только если** `(dword_6FAB6A34 & 3) == 0`, обнулить целиком
   16-битную плоскость `fogTable+0x30` через `memset` с размером
   `(fogTable+0x6C << fogTable+0x68) * 2` байт (`0x6F40A959`–`0x6F40A96F`).
3. Пройти первую группу fog-объектов через `0x6F40A7B0` (допуск по
   полям записи), затем список юнитов: собрать маску из временного
   массива, `unit+0x14C` и условных дополнительных запросов и вызвать
   `ApplyUnitFogRadius(unit, mask, 0, 0)` (`0x6F40AC36`–`0x6F40AC42`).
4. Пройти вторую группу fog-объектов через `0x6F40A7B0`, затем снять
   бит `2` с `fogTable+0x24` (`0x6F40AC61`). Группы различаются проверкой
   бита `0x100` в записи объекта.

`0x6F40A7B0` по младшим трём битам состояния fog-объекта выбирает
режим прямоугольного или радиального writer. Это показывает, что rebuild
включает источники карты и юнитов в установленном порядке. Семантика
записи клетки для режимов `1/2/4` разобрана в
[FND-0021](FND-0021-map-fog-writer-modes.md), жизненный цикл модификатора —
в [FND-0025](FND-0025-fog-modifier-lifecycle.md). Итоговая видимость после
всех источников требует отдельной проверки.

## Основание и контроли

Положительный статический контроль: при валидном втором игроке,
ненулевом `record[B]+0x34` и нулевых младших двух битах глобального слова
видна непрерывная цепь `Enable/Disable` → `0x6F41B4C0` →
`0x6F408070` → `0x6F40A8F0` → обнуление `+0x30` → повторное
нанесение допущенных fog-объектов и юнитов. Первый callback
зарегистрирован с кодом `0x50` через `0x6F549660` в `0x6F440DB0`;
`0x6F440F70` снимает регистрацию через `0x6F545B70`.

Отрицательные контроли: индекс второго игрока `>=16` выходит в начале
callback; нулевой `record[B]+0x34` минует rebuild. Если
`(dword_6FAB6A34 & 3) != 0`, `0x6F40A8F0` **пропускает `memset`**
плоскости `+0x30`, хотя остальные проходы продолжаются. Тип отношения
`9` всегда пропущен именно в этом callback. Эти ветви запрещают
трактовать путь как безусловный отзыв видимости при любой смене альянса.
