## Вывод

`0x6F296910` разрешает или создаёт блок по handle-ref **`unit+0x13C`**,
передаёт индекс игрока и булево значение в `0x6F27A430`, затем вызывает
`0x6F284D30` и `0x6F284DA0`. Последний пересчитывает маски самого юнита
`+0x148/+0x14C` из чтения этого блока. Это отдельный маршрут от
`JASS_IsUnitDetected`: его `CUnit::QueryDetection` (`0x6F27A320`)
разрешает **`unit+0x130`**. Общий add/remove эффекта
`0x6F296680`/`0x6F284A50` тоже использует `+0x130`, тогда как путь
`CBuffSharedVision` `0x6F2967F0`/`0x6F28DC80` изменяет блок `+0x13C`;
связь последнего разобрана в
[FND-0020](FND-0020-detection-revocation.md).

Внутри блока `+0x13C` `0x6F27A430(index, true)` устанавливает бит
`1 << index` в слове `block+0x24` **без увеличения** счётчика
`block+0x2C+4*index`. `0x6F27A430(index, false)` снимает этот бит,
только если счётчик уже равен нулю. Счётчиковая пара
`0x6F27A3C0`/`0x6F27A400` увеличивает/уменьшает счётчик и соответственно
ставит бит или снимает его при достижении нуля. Значит, для этого блока
правило `бит установлен ⇔ счётчик ненулевой` не является инвариантом:
прямой писатель может удерживать бит без счётчикового источника.

`0x6F27A460` берёт `block+0x24` по `unit+0x13C` и может добавить к нему
маску из способности при отдельном флаге юнита. Поэтому один лишь
`QueryDetection` по `+0x130` не описывает маску юнита, полученную из
`+0x13C`. Обратное тоже неверно: установленный прямым писателем бит
`+0x13C` сам по себе не доказывает положительный `JASS_IsUnitDetected`.

## Контроли и границы

Положительный статический контроль: если счётчик блока `+0x13C` для
игрока `i` равен `0`, а бит снят, вызов `0x6F27A430(i, true)` ставит
бит, не меняя счётчик; последующий `0x6F27A430(i, false)` снимает его.
Если счётчик положителен, `false` не снимает бит, сохраняя действие
счётчикового источника. Это **контрпример для модели только из счётчиков**,
а не утверждение, что указанная последовательность достижима штатной картой.

Отрицательные контроли: `0x6F27A430(i, false)` при ненулевом счётчике
не очищает слово `+0x24`; сам `0x6F27A430` не записывает массив
`+0x2C+4*i`. `0x6F27A320` читает `unit+0x130`, поэтому его ответ не
может измениться **непосредственно** от записи в другой блок `+0x13C`.
Косвенные игровые последствия последующего пересчёта этим не исключены.

В адресных IDA-телах S11 прямой вызов `0x6F27A430` найден из
`0x6F296910`; прямой caller самой обёртки не найден. Возможен непрямой
вызов через таблицу или иной маршрут, который этот поиск не раскрывает.
Не установлены игровые события установки/снятия override, все писатели
`+0x13C`, порядок с `CBuffSharedVision`, индексы вне штатного диапазона,
клиентское раскрытие после отзыва и эквивалентность исходной DLL.
Статусы S11: `0x6F296910`, `0x6F27A430`, счётчиковая пара — `TODO`;
`0x6F27A460` и `0x6F284DA0` — `DIFFERS`.

Следующий опыт: в двухигроковой сцене получить оба типа источника одного
бита раздельно, затем отзывать их в обоих порядках; на каждом шаге
сравнивать счётчик и слово блока `+0x13C`, отдельный блок `+0x130`,
`unit+0x148/+0x14C`, JASS-запросы и наблюдаемый UI. Игрок без обзора
служит отрицательным контролем. Условия создания прямого override сначала
нужно установить, не подменяя поля памяти как будто это штатное событие.
