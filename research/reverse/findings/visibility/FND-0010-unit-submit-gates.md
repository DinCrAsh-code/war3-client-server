## Вывод

`SPlayerTable::SubmitUnit` не сводится к чтению fog-клетки. В IDA-потоке
перед чтением сетки есть проверка отношения/состояния юнита, затем возможен
ранний ответ `1` по флагу; только оставшийся путь получает координаты юнита,
спрашивает сетку, при необходимости записывает полный код в `out` и
возвращает результат пересечения кода с запрошенной маской. Это уточняет
[FND-0007](FND-0007-player-visibility-routes.md).

## Основание и статические контроли

Состояние адресов в S11: `0x6F3A38F0` и его sibling `0x6F3A3830` —
`TODO`, `claimed_by: null`; сами IDA-тела доступны. Вызывающий
`CUnit::SubmitToPlayerTable` уже имеет C++-тело, но для `SubmitUnit`
в S10 остаётся redirect. По инструкциям `0x6F3A38F0`:

1. Явный индекс игрока превращается в однобитную маску (с усечением до
   16 бит). Из записи игрока читается слово `+0x2E0`.
2. При нулевом бите 1 флагов вызывается `0x6F3A15F0` с юнитом, этим
   словом и битом 2 флагов. Если вызов вернул ноль, функция возвращает
   ноль до запроса сетки. При установленном бите 1 этот вызов пропускается.
3. После успешной/пропущенной проверки бит 0 даёт ранний ответ `1`;
   `out` на этом пути не записывается. Значение и назначение бита пока
   нельзя честно называть «видимостью» или «правом раскрытия».
4. Иначе виртуальный вызов юнита через слот `+0xB8` и
   `SUnitMovement::GetCellMidpoint` (`0x6F474460`) дают координаты. После
   сдвига обеих на 2 вызывается `SubmitFromGrid` (`0x6F00E830`) с
   однобитной маской игрока. Полный код пишется через ненулевой `out`,
   затем ответ сравнивается с аргументом запрошенных состояний.

Положительный статический контроль: на пути без раннего выхода видны
`call 0x6F00E830`, запись `[out]` при ненулевом указателе и `and` с
запрошенной маской. Отрицательные контроли: неуспешная проверка
`0x6F3A15F0` обходит сетку; бит 0 обходит её после проверки и не пишет
`out`. В sibling `0x6F3A3830` та же форма проверки/запроса, но входные
маски берутся из полей `+0x3C`/`+0x40` объекта `+0x34`, а не из явного
индекса и записи игрока `+0x2E0`.

Даже этот ответ не равен окончательному ответу `CUnit::SubmitToPlayerTable`:
вызывающий код после нуля дополнительно проверяет бит юнита через
`TestBit(playerIndex)`. JASS и сетка точки имеют другие маршруты.

## Ограничения и значение для проекта

Это анализ IDA-текста и опубликованного C++, без исполнения Game.dll и
собственного сравнения машинных байтов с исходным образом. Значения битов,
источник маски `+0x2E0`, смысл виртуального слота, динамический порядок
обновлений и право на отдельные поля юнита не установлены. Отсутствие
записи `out` на ранних путях требует проверки у конкретных вызывающих:
нельзя автоматически считать его нулём или свежим кодом.

Следующий опыт: для двух игроков менять ровно один вход — обзор, флаг,
отношение или детект — и сопоставлять `SubmitUnit`, `IsUnitVisible`,
`IsUnitDetected` и локальный UI. Контрольный игрок не имеет обзора. Только
после этого можно проектировать серверное решение о выдаче состояния и
клиентское представление без скрытого мира.

Адресный разбор раннего gate и его отличия от двухканального `IsUnitDetected`
продолжен в [FND-0014](FND-0014-submit-detection-gate.md). В частности,
повторный тест из `0x6F3A15F0` спрашивает только первый канал детекта.
