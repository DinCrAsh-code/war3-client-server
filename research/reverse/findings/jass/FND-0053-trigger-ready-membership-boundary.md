## Вывод

После route-level разрешения sender ([FND-0051](FND-0051-resume-sender-resolution.md)) оба командных обработчика проверяют живой и подходящий trigger agent. Их **локальные** условия продолжения различаются: `ResumeTriggerExec` сверяет token с `CTriggerExecution+0x90`, а `TriggerSyncReady` передаёт sender в функцию, которая без предварительной проверки его membership снимает бит `1 << sender` с маски `CTriggerExecution+0x8C`. Если оставшаяся маска нулевая, она вызывает общий обход trigger. Общий обход дополнительно возвращается сразу при ненулевом `CTriggerExecution+0x80`, которое в соседних функциях выступает числом ожидаемых вложенных execution objects в массиве `+0x84`.

Это граница локальной проверки состояния **конкретного execution**. Ни token resume, ни маска ready сами по себе не подтверждают сетевую личность peer или его право на trigger. Отсутствие проверки прежнего бита sender в показанном ready handler не означает глобального отсутствия авторизации в транспорте или вызывающем dispatch.

## Адресный маршрут и контроли

1. [`0x6F440620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440620.json) и [`0x6F440730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440730.json) начинают одинаково: разрешают command `+0x18/+0x1C` через [`0x6F03FA30`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F03FA30.json), проверяют marker `+agl` (`0x2B61676C`), получают вложенный execution через [`0x6F39FF70`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F39FF70.json), повторно проверяют его agent handle и требуют `agent+0x20==0`. При null/неверном marker/pending состоянии соответствующий `0x6F447700` или `0x6F447720` не вызывается. Это отрицательный контроль **живости и типа объекта**, не проверка sender-owner. Подробности payload и type-tag находятся в [FND-0044](FND-0044-trigger-continuation-command-identity.md).
2. Resume handler не читает command `+0x15` как sender для trigger-local проверки; он передаёт token `+0x20` в [`0x6F447700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447700.json). Тот сравнивает его с `execution+0x90`, при несовпадении возвращается; при совпадении **сначала** увеличивает `+0x90`, затем вызывает [`0x6F447340`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447340.json). У последнего верхний gate `execution+0x80 != 0 → return`. Поэтому совпавший token допускает вход в общий обход, но не гарантирует запуск action при ожидаемых вложенных execution objects. Устаревший token — отдельный отрицательный контроль, уже до этого gate.
3. Маска ready формируется [`0x6F445120`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F445120.json): очистить `execution+0x8C`, пройти индексы игроков `0..11`, поставить бит только при `player+0x270==1` и `player+0x268==0`. Это набор ожидаемых **слотов игроков на момент построения**, а не поле отдельного владельца trigger. [FND-0042](FND-0042-trigger-sync-barrier.md) устанавливает связь этой операции с веткой `TriggerSyncStart` и последующей командой ready.
4. Ready handler передаёт command `+0x15` в [`0x6F447720`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447720.json). Первые инструкции делают `mask &= ~(1 << sender)`; до этого нет сравнения `sender<12` и нет `mask & (1 << sender)` как условия допуска. Затем функция проходит те же 12 player slots и снимает уже ожидаемые биты для игроков, у которых одновременно `+0x268!=0` и `+0x270!=1`; при `mask!=0` выходит, при `mask==0` вызывает `0x6F447340`. Отрицательный контроль: посторонний sender, чей бит **отсутствует**, не уменьшит ненулевую маску этим действием; однако при маске, уже равной нулю, локальная функция всё равно попробует общий обход. Его верхний gate `+0x80` и последующие состояния могут остановить эффект. Это не доказательство повторного выполнения action от duplicate ready.
5. Смысл `+0x80` ограниченно подтверждают [`0x6F446BB0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F446BB0.json) и [`0x6F446C60`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F446C60.json): обе обходят `+0x84` как массив указателей длиной `+0x80`, первая не добавляет повторный объект, вторая удаляет объект и при нулевой длине посылает новый resume с текущим `+0x90`. [Конструктор `0x6F446010`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F446010.json) инициализирует `+0x80/+0x84` нулём. Следовательно, верхний gate общего обхода связан с незавершёнными вложенными executions; он не сверяет sender команды.

## Ограничения и отвергнутые гипотезы

В `0x6F447720` нет локального membership/range gate для sender, но sender уже прошёл разбор сетевого subrecord, lookup в per-record таблице и action gate из [FND-0051](FND-0051-resume-sender-resolution.md). Статически не установлены транспортная аутентификация key, право peer выдавать `0x63`, штатная возможность sender вне `0..11`, точный порядок ready при отключении игрока и жизненный цикл trigger после нулевой маски. Нельзя объявлять отсутствие глобальной авторизации или достижимый replay/duplicate баг по одному handler. `+0x80` — наблюдаемая длина массива и ранний gate, но не универсальное описание всех состояний execution; дальнейшая логика `0x6F447340` также содержит проверки `+0x78`, списка actions и lifecycle. ## Значение для проекта

В серверной модели нужно проверять три независимых условия: authenticated sender принадлежит сессии, этот sender входит в ожидаемое множество конкретного sync barrier, и token/epoch относится к живому execution. Оригинальный route-level lookup и trigger-local mask/token показывают, где проходят эффекты и отказы, но не задают готовую политику доверия. Следующий динамический контроль: один ожидаемый и один посторонний sender, ready до/после обнуления маски, stale/correct resume token и ненулевой `+0x80`; наблюдать вызов `0x6F447340` отдельно от фактического выполнения action.
