## Вывод

Проверка `0x6F53F160`, от которой зависит [GetLocalPlayer](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3BBB60.json), читает из TLS slot `13` активный индекс **сетевой записи** `+0x610`, а не доказанный неизменный режим матча. Когда он равен `1`, натив выбирает слово `CGameWar3+0x2A`; иначе — `+0x28`. В S11 есть условный писатель индекса сетевой записи, установление `+0x28` при разборе игроков и копирование `+0x28 → +0x2A` при инициализации мира. Следовательно, один только сохранённый JASS instance/token не фиксирует результат следующего вызова `GetLocalPlayer`: результат зависит от состояния этих объектов в момент вызова. Это **статическая зависимость**, не наблюдение смены локального игрока между `TriggerSleepAction` и `ResumeTriggerExec`.

## Адресный маршрут и контроли

1. [`0x6F4C34D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F4C34D0.json) выбирает slot `13` из привязанного к текущему EvtContext TLS array ([FND-0048](FND-0048-event-context-tls-rebinding.md)). [`0x6F53F160`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53F160.json) затем идёт по `slot13+0x10 → cache+0x08 → net session+0x610` и проверяет равенство `1`. Тот же pointer chain в сетевом callback [`0x6F5538F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5538F0.json) получает `self` для [`0x6F553470`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F553470.json). У сетевого конструктора [`0x6F550460`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550460.json) две записи по `0x304` байта лежат в `+0x08..+0x60F`, а `+0x610` инициализируется нулём. Сетевой dispatcher индексирует запись как `self + index*0x304` и проверяет её `+0x278`; [S10 layout](../../../../src/Net/netdata.h) называет `+0x610` `SNetSessionInfo::m_activeIndex`. Название `IsGameModeOne` в [S10](../../../../src/Game/gamemode.cpp) описывает булеву проверку, но не устанавливает самостоятельный lifetime «режима игры».
2. В [`0x6F551D80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551D80.json) record byte `+0x15` выбирает текущий active index либо `0`; только при `slot == active` тип `0x10` или `0x15` входит в route-candidate ветвь. Если route record `self+0x278+slot*0x304` имеет состояние `<1` и reader [`0x6F652560`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F652560.json) не превысил длину, ветвь сначала ставит `+0x610=0`, а при бите `0x100` прочитанного probe ставит `+0x610=1`. [S10 dispatcher](../../../../src/Net/netevent_dispatch.cpp) содержит реконструкцию той же ветви. Отрицательные контроли: другой slot, уже активная route record и parse overrun не проходят этот писатель; при сброшенном бите `0x100` конечный индекс остаётся `0`. Это доказывает условный **write site**, но не его вызов между двумя конкретными JASS callbacks.
3. [`CGameWar3` constructor `0x6F3AF3B0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3AF3B0.json) задаёт слову `+0x28` начальное значение `0x10`. В lobby/player setup [`0x6F5C0830`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C0830.json) сохраняет singleton `dword_6FAB65F4`, разбирает player records, и пишет `world+0x28=bx` лишь когда выбранный slot `bx` равен результату `0x6F53EDD0`; его caller [`0x6F5C37A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C37A0.json) проверяет успешность разбора. Другой путь [`0x6F5C0EE0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C0EE0.json), вызванный [`0x6F5C1270`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C1270.json), делает аналогичное присваивание при разборе config records, с альтернативной веткой по сравнению с `0x11DC`. Это положительные контроли того, что `+0x28` не константа конструктора; они не доказывают изменение уже во время игрового trigger.
4. [`CGameWar3::Load`, `0x6F3B0B70`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3B0B70.json) передаёт адрес `world+0x28` в word reader `0x6F4C2C70`; [S10 Load](../../../../src/Game/gamewar3load.cpp) подтверждает этот out-param. В успешном пути [`0x6F3B0750`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3B0750.json), вызываемом [`0x6F5C4030`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C4030.json), результат `0x6F53F160` сохраняется в `world+0x3C8`, а позднее `0x6F3B0A85/89` копирует `word +0x28` в `word +0x2A`. Ранний нулевой результат `0x6F01DE80` уходит на выход `0x6F3B0B3C` до этой копии — отрицательный контроль для snapshot. Наконец, при создании score screen [`0x6F5A78F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5A78F0.json) копирует `+0x2A → +0x28`, только если singleton существует и `world+0x3C8 != 0`. Это поздний write site `+0x28`, а не доказанная операция посреди матча.
5. [GetLocalPlayer `0x6F3BBB60`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3BBB60.json) при null singleton возвращает `0`; при active index `1` берёт `word +0x2A`, иначе `word +0x28`, затем получает player object и handle ([FND-0043](FND-0043-local-player-handle-selection.md)). По [FND-0044](FND-0044-trigger-continuation-command-identity.md) `ResumeTriggerExec` передаёт handle/type/token execution object без этих двух player slots и active index. Поэтому новый вызов натива после возобновления вновь читает состояние текущего EvtContext; он не извлекает player slot из payload команды.

## Ограничения и отвергнутые гипотезы

Наличие writers `+0x610`, `+0x28` и snapshot `+0x2A` опровергает трактовку этих полей как неизменных констант всего процесса. Оно **не доказывает** фактическую смену сетевого active index или local-player result между `TriggerSleepAction` и `ResumeTriggerExec`, штатную достижимость route-candidate ветви в ходе матча, последующие записи в `+0x2A` либо сохранность самих объектов после teardown. Обследованные записи S11 не являются исчерпывающим whole-program alias analysis; другие косвенные писатели и nested effects не исключены. Context-bound TLS array из FND-0048 связывает callbacks с EvtContext при указанном маршруте, но не замораживает содержимое slots `5/13` и вложенного net session. Статусы S11 здесь включают `EXACT`, `DIFFERS` и `TODO`; статический вывод не означает byte match цепи или собственный runtime experiment.

## Значение для проекта

Для разделения общего и локального JASS нужно задать явный момент разрешения local-player identity: при каждом вызове `GetLocalPlayer` либо на границе continuation по проверяемому контексту. Оригинальная команда resume сама этого выбора не переносит. Следующая проверка: в двух player contexts зарегистрировать TLS array/key, `net session+0x610`, `world+0x28/+0x2A`, результат `GetLocalPlayer` до и после `TriggerSleepAction`, а также типы `0x10/0x15` и token принятой команды. Отдельно пройти отрицательные ветви несовпавшего token, route state `>=1` и отсутствующего singleton; только динамический маршрут покажет, какие изменения возможны именно в матче.
