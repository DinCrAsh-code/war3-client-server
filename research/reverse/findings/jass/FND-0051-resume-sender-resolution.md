## Вывод

В показанном входном пути `ResumeTriggerExec` и `TriggerSyncReady` получают `sender` из **таблицы участников выбранной сетевой записи**. Внешний event byte `+0x15` выбирает record index `0` либо текущий `SNetSessionInfo+0x610`; внутри turn subrecord отдельный байт sender-key разрешается в этом record через hash table в участника, чей byte `+0x36` становится sender команды. Неизвестный ключ даёт `0xFF`, и `FireCommand` не публикует такую команду observers. Дополнительный action gate может подавить builder ещё до его публикации, причём его ветви для record `0` и record `!=0` различаются.

Это доказанная **локальная маршрутизация и проверка допустимости action**; она не доказывает аутентификацию источника пакета, привязку сетевого peer к sender-key или право данного sender возобновлять конкретный `CTriggerExecution`. Проверки handle/type/token и ready mask внутри trigger описаны отдельно в [FND-0044](FND-0044-trigger-continuation-command-identity.md).

## Адресный маршрут и контроли

1. [`0x6F551D80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551D80.json) читает `record+0x14` как event type, а `record+0x15` как флаг выбора сетевой записи: ненулевой берёт `self+0x610`, нулевой берёт индекс `0`. Для queued turn event cases `0x1F/0x20` он передаёт этот индекс в [`0x6F5516E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5516E0.json), откуда тот попадает в [`0x6F550730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550730.json). [S10 event dispatcher](../../../../src/Net/netevent_dispatch.cpp) и [action dispatcher](../../../../src/Net/netcommand_dispatch.cpp) дают читаемую сверку. Отрицательный контроль: `record+0x15` сам по себе не является player ID внутри action и не заменяет sender-key subrecord.
2. `0x6F550730` сначала читает счётчик и затем через [`0x6F652300`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F652300.json) получает байт sender-key и length-prefixed payload одного subrecord. Он формирует адрес таблицы как `self + recordIndex*0x304 + 0x290` и передаёт key в [`0x6F54E7E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54E7E0.json) → [`0x6F54E7C0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54E7C0.json) → [`0x6F54C870`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54C870.json). Lookup сравнивает сохранённый key с входным; `0x6F54E7E0` при найденной записи читает `entry+0x36`, а при null возвращает `0xFF`. Отдельный inner reader над length-prefixed payload читает action byte `0x62` или `0x63`. Граница длины outer stream и предел payload `0x400` находятся до builder; overrun даёт parse-error/выход, а не подтверждение отправителя. [S10](../../../../src/Net/netcommand_dispatch.cpp) моделирует те же два вложенных уровня разбора.
3. Положительный контроль происхождения таблицы: [`0x6F5496A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5496A0.json) берёт сетевую запись через TLS slot `13` и передаёт её `+0x290` вместе с key/player ID в [`0x6F5491D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5491D0.json). Тот переводит найденный по key participant pointer из одного slot array в player array и записывает ID в `participant+0x36`. Наблюдаемые callers `0x6F5496A0` — player/config paths [`0x6F5C0830`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C0830.json) и [`0x6F5C0EE0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5C0EE0.json). Это доказывает локальное присвоение player ID уже существующему participant key; доверенность самого поступившего key не следует из этих функций.
4. Есть и путь отзыва: [`0x6F54FDF0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54FDF0.json), связанный в S10 с player-leave event, берёт event record index `+0x10` и key `+0x18`, затем вызывает [`0x6F54E800`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54E800.json) на таблице `self + index*0x304 + 0x290`. Последний убирает participant из slot array и hash table. [`0x6F54C380`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54C380.json) при reset сетевой записи вызывает [`0x6F54B1A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54B1A0.json) для очистки этой таблицы. После успешного удаления старый key не должен разрешаться **этой таблицей**; порядок и доставка event относительно in-flight turn не проверены.
5. Второй gate у [`0x6F550730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550730.json) зависит от `recordIndex`. Для `0` значение `sender>0x0C` даёт `suppress=1`; при `sender<=0x0C` он получает player holder через `0x6F3A1650` и вызывает [`0x6F545270`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F545270.json) с action byte. При null holder функция подавляет action. При `holder+0x270==1` и нулевом результате `0x6F473170(holder+0xF0)` разрешает action раньше switch; иначе switch разрешает `0x62` и подавляет `0x63` по default. Для `recordIndex!=0` этот gate пропускается с `suppress=0`. Положительный контроль: S11 cases `0x62/0x63` в `0x6F550730` действительно передают полученные `sender` и `suppress` соответственно в [`0x6F542620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F542620.json) / [`0x6F542700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F542700.json). Подавление action и отказ конкретного trigger по token/handle — разные этапы.
6. Последний отрицательный контроль для unknown key: даже если `recordIndex!=0` обошёл action gate, оба builder используют `FireCommand` с условием `sender!=0xFF` перед observer delivery ([`0x6F53C290`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53C290.json) для `0x62`; соответствующий адрес `0x63` проверен в [FND-0044](FND-0044-trigger-continuation-command-identity.md)). Поэтому miss в sender lookup по этому маршруту не вызывает trigger handler. Это **локальный** отказ; он не подтверждает, кто уполномочил существующую запись таблицы.

## Ограничения и отвергнутые гипотезы

Факт разрешения wire key через hash table и проверки player action не является доказательством сетевой аутентификации или авторизации `ResumeTriggerExec` для данного trigger. В просмотренных `0x6F551D80`, `0x6F550730`, `0x6F542620/2700` и trigger handlers нет доказанного сравнения peer identity с key либо sender с owner `CTriggerExecution`; транспортный приём, создание первоначальной participant entry, привязка peer к key, replay/delay после удаления и server-side policy вне этой цепи. Отсутствие проверки в выбранных функциях не исключает её в другом слое. Также статически не доказано, какой `recordIndex` штатный для `0x62/0x63` в матче, поэтому различие action gate `0`/`!=0` не следует превращать в глобальное правило «ready всегда разрешён/запрещён». Статусы S11 смешанные (`EXACT`/`DIFFERS`/`TODO`), собственного прогона DLL и fingerprint нет.

## Значение для проекта

Для авторитетного сервера входная команда должна иметь проверенную связь `connection → session/record → sender`, а проверка `sender → право на trigger/epoch` должна быть отдельным контрактом. Оригинал даёт конкретные отрицательные ветви для неизвестного key, сброшенной таблицы и недопустимого action, но не готовую серверную авторизацию. Следующий опыт: два peer с разными зарегистрированными keys, один неизвестный и один удалённый key, оба record indices, `0x62/0x63`, живой и stale token; записать, где команда отбрасывается до observer и где уже внутри trigger.
