## Вывод

В оригинальном командном пути `ResumeTriggerExec` (`0xA0062`) передаёт пару handle/type **и отдельный token исполнения**; обработчик пропускает повторный обход лишь при совпадении token с `CTriggerExecution+0x90` и затем увеличивает это поле. `TriggerSyncReady` (`0xA0063`) передаёт только пару handle/type; обработчик использует байт отправителя из оболочки команды для снятия бита с `CTriggerExecution+0x8C`. Оба пути проверяют живость и тип объекта, но эти проверки нельзя считать доказательством авторитетности отправителя в новой клиент-серверной архитектуре.

| Команда | Поля объекта команды | Проверка перед эффектом |
|---|---|---|
| `ResumeTriggerExec`, `0xA0062` / `0x62` | `+0x18` handle, `+0x1C` type, `+0x20` token; `+0x15` sender | Живой `CTriggerExecution`, затем `token == execution+0x90`; при совпадении `+0x90++` и повторный обход |
| `TriggerSyncReady`, `0xA0063` / `0x63` | `+0x18` handle, `+0x1C` type; `+0x15` sender | Живой `CTriggerExecution`; sender используется как индекс бита mask `+0x8C`, отдельного token нет |

## Основание и контроли

1. Отправители [`0x6F43F620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F43F620.json) и [`0x6F43F720`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F43F720.json) читают у переданного execution agent пару `+0x0C/+0x10` после `LookupHandle`, проверки `+agl` (`0x2B61676C`) и `pending+0x20==0`. При провале они подставляют `-1` в пару. Первый отправитель добавляет входной token третьим payload dword и строит `CNetCommandResumeTriggerExec` с ID `0xA0062`; второй строит `CNetCommandTriggerSyncReady` с ID `0xA0063` без token. Вызовы из [FND-0041](FND-0041-trigger-action-continuation.md) и [FND-0042](FND-0042-trigger-sync-barrier.md) показывают, откуда приходят token и сигнал ready.
2. Получатели [`0x6F542620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F542620.json) и [`0x6F542700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F542700.json) конструируют соответствующие команды, записывают sender из параметра dispatch в байт `+0x15`, читают соответственно три или два dword через [`0x6F554D20`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F554D20.json) / [`0x6F554D70`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F554D70.json) и проверяют выход за заявленную длину перед `FireCommand` (если dispatch не подавлен). [S10 `netcommand_dispatch.cpp`](../../../../src/Net/netcommand_dispatch.cpp) сопоставляет action bytes `98/99` этим builder-функциям; [base-layout](../../../../src/Net/netcommand.h) отделяет sender `+0x15` от payload. Отрицательный контроль parser: переполнение заявленной длины приводит к parse-error и не вызывает `FireCommand` по этой ветке.
3. [`FireCommand`, 0x6F53B790](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53B790.json) пропускает публикацию в observer lists, когда sender равен `0xFF`. Регистрация [`0x6F440DB0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440DB0.json) и [`0x6F440F70`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440F70.json) сопоставляет подтипы `0x62/0x63` с обработчиками [`0x6F440620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440620.json) и [`0x6F440730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440730.json). Это контроль, что две одинаково начинающиеся payload-пары направляются в разные эффекты.
4. Оба обработчика разрешают пару через [`LookupHandle`, 0x6F03FA30](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F03FA30.json), проверяют `+agl` и `pending+0x20==0`, затем тип вложенного agent через [`0x6F39FF70`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F39FF70.json) и повторно проверяют его handle. Его type-leaf [`0x6F443C60`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F443C60.json) возвращает `+tex` (`0x2B746578`); [vtable `CTriggerExecution`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/classes/0x6F950C14.json) указывает на [`0x6F443C90`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F443C90.json), возвращающий тот же `+tex`. Поэтому название S10 `SCheckedTextAgentSlot` не является основанием считать получателя UI-текстом: здесь тип совпадает с execution object.
5. После этих проверок `0x6F440620` берёт token из command `+0x20` и вызывает [`0x6F447700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447700.json): при несовпадении с execution `+0x90` возврат без запуска, при совпадении `+0x90` увеличивается до вызова `0x6F447340`. В `0x6F440730` такого token нет: handler берёт sender из `command+0x15` и вызывает [`0x6F447720`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447720.json), снимающий соответствующий бит с mask `+0x8C`. Внутри этих двух handlers нет явной проверки, что sender вправе возобновить данный execution или объявить ready для этого trigger; это предел локального статического маршрута, не утверждение о проверках внешнего транспорта.

## Ограничения и отвергнутые гипотезы

`LookupHandle` в [S10](../../../../src/Agent/handle.cpp) проверяет индекс, состояние слота и type tag; это не доказательство generation-protection при повторном использовании слота. Token `+0x90` — отдельный счётчик данного execution (инициализация `1` в [`0x6F447E10`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447E10.json)); его совпадение отсекает устаревшую команду лишь в пределах показанного состояния объекта. Глобальная уникальность token, replay-защита между жизненными циклами handle, аутентификация sender, авторизация по игроку, доставка и порядок команд здесь не доказаны. `DIFFERS`/`MISMATCH` статусы S11 builder/attach запрещают считать S10 byte-matched оригиналом; указанные поля сверены с сырыми записями S11. Динамические контроли не запускались.

## Значение для проекта

Для будущего авторитетного сервера нужно явное право на `ready` и `resume`, привязанное к серверному trigger/epoch и отправителю. Оригинальный handle-путь и token-проверка показывают, какие идентичности и отрицательные ветви нельзя потерять ради совместимости, но не задают готовую границу доверия для нового протокола. Следующий эксперимент: один действительный и один недействительный handle, совпавший и устаревший token, ready от ожидаемого и постороннего слота; проверить состояние mask и факт повторного входа.
