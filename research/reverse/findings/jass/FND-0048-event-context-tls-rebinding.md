## Вывод

Для показанного запуска `GameMain` первичный callback `0x6F008420` и зарегистрированный им сетевой pump `0x6F5538F0` привязаны к **одному EvtContext**, а не к номеру OS thread. EvtContext хранит указатель на собственный TLS array в `+0x208`; worker перед обработкой выбранного контекста устанавливает этот указатель в Win32 TLS и записывает в его slot `0` ключ контекста. Первичный callback заполняет slots `13` и `5` через общий `SetThreadLocalSlot`; сетевой pump позже вызывается из списка handler slot `5` этого EvtContext и читает slots того же массива. Это сужает [FND-0047](FND-0047-resume-dispatch-tls-boundary.md): физический поток может меняться, но при доставке через тот же живой EvtContext повторный JASS instance lookup использует его сохранённую таблицу. Статический путь не доказывает фактическую миграцию OS thread, неизменность содержимого slots между вызовами или сохранность контекста после teardown.

## Ограничения и отвергнутые гипотезы

Совпадение TLS **array** здесь следует из object identity EvtContext, выдаваемого по `context+0x0C`, и worker rebinding; совпадение **OS thread** не требуется и не установлено. Доказательство условно успешным созданием и регистрацией EvtContext, сохранением его key в TLS slot `0`, сохранностью объекта и отсутствием чужой перезаписи slots `5/13` между callbacks. Большой startup callback содержит косвенные вызовы, для которых не выполнен исчерпывающий audit side effects; поэтому это не claim о невозможности смены TLS0 внутри любого nested path. Не прослежено, какой worker фактически исполняет два callback, когда именно приходит сетевой event slot `5`, каким образом исходящий command становится входящей queued записью, и выполняются ли все виды `TriggerSleepAction` именно в этом EvtContext. Статус S11 для части scheduler функций `THUNK`/`TODO`/`DIFFERS`; byte-match whole chain и динамический прогон отсутствуют.

## Значение для проекта

При переносе JASS-продолжений в клиент-серверную модель context ID и связанная с ним таблица JASS instance должны жить как единый execution context независимо от thread pool. Проверка границы: логировать key TLS slot `0`, адрес TLS array, значения slots `5/13` и OS thread ID при первом slot `7`, перед сетевым slot `5`, на `TriggerSleepAction` и в `JassThreadGetInstance`; затем повторить при migration между workers и после unregister pump. Отдельно проверить, что другой EvtContext не разрешает сохранённый instance key чужой таблицей.
