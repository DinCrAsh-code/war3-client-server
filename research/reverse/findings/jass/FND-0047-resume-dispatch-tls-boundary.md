## Вывод

Неопределённость [FND-0046](FND-0046-local-player-context-after-trigger-sleep.md) сужается: при успешном стартовом входе движок устанавливает game-data в TLS slot `13`, обеспечивает JASS state в slot `5` и регистрирует сетевой pump как event handler. При последующем вызове pump **заново** читает slot `13` текущего OS thread и в его стеке вызывает разбор queued turn, builder `ResumeTriggerExec`, observer dispatch и trigger handler. Повторное разрешение JASS instance в handler читает slot `5` **этого же потока вызова**. В показанной цепи dispatch нет записи slots `5/13` и нет переключения OS thread. Это не связывает поток callback с исходным потоком, на котором `TriggerSleepAction` поставил сон: событие проходит через исходящую и входящую очереди, а вызывающий код event-handler slot `5` и thread affinity этой доставки здесь не установлены.

## Адресный маршрут и контроли

После этого тот же вход вызывает [`0x6F3D4020`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3D4020.json), чей первый вызов — [`0x6F453C00`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F453C00.json): получить slot `5`, при пустом — создать `JassThreadLocal` и записать его тем же `0x6F4C34F0`. Затем `0x6F008420` вызывает [`0x6F553920`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F553920.json), который регистрирует [`0x6F5538F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5538F0.json) в event slot `5` через [`0x6F62B390`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F62B390.json). **Event slot `5` и TLS slot `5` — разные таблицы**, совпадение числа не означает общего owner. `0x6F62B390` ищет event bucket по ключу из TLS slot `0`; этот путь регистрации сам по себе не устанавливает, какой OS thread позже выполнит callback. S10 [инициализация net](../../../../src/Net/netdata_initconfig.cpp) и [регистрация event handler](../../../../src/Frame/eventregister.cpp) подтверждают структуру вызовов, не runtime affinity.
2. При входе в callback `0x6F5538F0` вызывает [`0x6F4C34D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F4C34D0.json) с `slot=13`, берёт из него net-data records и прямо вызывает [`0x6F553470`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F553470.json). При queued record с обычным типом `0x6F5530D0` вызывает [`0x6F551D80`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F551D80.json), чьи варианты turn-record вызывают [`0x6F5516E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5516E0.json) → [`0x6F550730`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F550730.json). Это положительный контроль маршрута именно данного action; иной byte выбирает другой case или default, не builder `ResumeTriggerExec`.
3. При неснятом suppress flag и корректной длине `0x6F542620` вызывает [`0x6F53C290`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F53C290.json) — отдельную копию `FireCommand` для этого builder, с тем же sender `!=0xFF` gate, что и `0x6F53B790` из [FND-0044](FND-0044-trigger-continuation-command-identity.md). Далее [`0x6F5378E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F5378E0.json) синхронно вызывает два observer lists; их [`0x6F629A90`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F629A90.json) → [`0x6F62A7B0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F62A7B0.json) → [`0x6F62A5D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F62A5D0.json) доставляют совпавший message непосредственным vtable-call зарегистрированному resource. Для `0x62` регистрация ведёт к [`0x6F440620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440620.json) ([FND-0044](FND-0044-trigger-continuation-command-identity.md)); тот при действительном handle передаёт token в [`0x6F447700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447700.json). При несовпавшем token `0x6F447700` не вызывает `0x6F447340`; это второй отрицательный контроль.
4. После совпадения token `0x6F447700` вызывает trigger action, и сохранённый instance key разрешается через [`0x6F449D10`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F449D10.json), который берёт slot `5` через `0x6F4C34D0` (точная связка в [FND-0046](FND-0046-local-player-context-after-trigger-sleep.md)). В синхронной цепи от callback `0x6F5538F0` до этого lookup не найден вызов [`0x6F4C34F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F4C34F0.json) для slots `5/13`: используются уже установленные значения **текущего** потока. Отрицательный контроль отсутствия контекста: `0x6F4C34D0` возвращает нуль при отсутствующем TLS array, а `0x6F5538F0` непосредственно читает `+0x10` результата; fallback к контексту спящего instance здесь не показан. Это статический precondition, не воспроизведённый crash.
5. Исходящая сторона задаёт границу доказательства: [`0x6F43D840`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F43D840.json) сериализует команду и вызывает [`0x6F54D970`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F54D970.json), который сам читает TLS slot `13`, сверяет переданный индекс с net-data `+0x610`, проверяет состояние выбранной записи и предел буфера `0x400` до записи. Неудовлетворённая проверка оставляет путь без записи — отрицательный контроль. Но между этой записью и queued record, который позже достаёт `0x6F5530D0`, находятся не прослеженные транспорт/очередь/вызов event callback; одинаковое число TLS slot в отправителе и получателе не доказывает одинаковый OS thread.

## Ограничения и отвергнутые гипотезы

Регистрация `0x6F5538F0` в event slot `5` не является доказательством выполнения на том же OS thread, что и стартовая регистрация, постановка sleep или исходящая сериализация. Внешний actor, вызывающий этот event callback, и перенос net record через очередь не восстановлены. Статическая цепь показывает прямые и виртуальные вызовы от callback к JASS lookup, но не исполненный runtime trace и не проверку отсутствия асинхронного вмешательства между ними. Даже при общем TLS array для начальной и получающей фаз не проверено, что singleton/режим/индекс local player остались неизменными. Значение `net-data+0x610` здесь оставлено полем проверки, без новой трактовки бизнес-режима. S11-статусы функций смешанные (`TODO`/`DIFFERS`/`THUNK`/`EXACT`); whole-chain byte matching и fingerprint не установлены.

## Значение для проекта

В будущем client-server исполнении сетевой callback должен получать определённый execution context: тот JASS instance table, где лежит сохранённый ключ, и тот game-data context, из которого нативы узнают локального игрока. Следующий контроль — на двух потоках записать OS thread ID и адреса TLS slots `5/13` при `TriggerSleepAction`, на отправке `ResumeTriggerExec`, при входе в event pump и перед lookup instance; затем сравнить результат повторного `GetLocalPlayer` и stale-token ветвь. Только эта проверка закроет оставшуюся thread-affinity границу.
