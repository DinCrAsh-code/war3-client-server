| Verification | source-reviewed |

| Sources | [S11](../../SOURCES.md#s11-адресный-корпус-ida-коллеги), commit `10950d496aa7357a6180c1956def50c2a3e8c1a9`; [S10](../../SOURCES.md#s10), commit `2fc76c8035554912dd66fc0a06a39eda376a806c` |

## Вывод

Если сохранённый trigger action после `TriggerSleepAction` содержит вызов `SetUnitState` и команда `ResumeTriggerExec` проходит проверки, VM исполняет этот native из прежнего JASS instance и opcode cursor. Для `state=2` и разрешённого живого unit его тело доходит до `CUnit::SetState`, затем до записи значения диапазона маны объекта мира. Проверка token относится к повторному **входу в trigger**, а проверка handle — к допустимости **конкретного unit**. В показанном участке `SetUnitState` не сверяет sender, `GetLocalPlayer` или локальный слот игрока и не содержит собственного счётчика «один раз на игрока».

Это условный контракт исполняемого пути, а не наблюдение конкретной карты. Один успешный `ResumeTriggerExec` не гарантирует даже одного изменения: обход может остановиться до action, handle может не разрешиться, state может быть не записываемым, а записанное значение может совпасть с прежним после ограничения диапазоном. Повторное выполнение и дублирование общего эффекта в целевой архитектуре не доказаны.

## Адресный маршрут и контроли

1. [`TriggerSleepAction`, `0x6F3B2DB0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3B2DB0.json) помечает текущий instance на выход со статусом `3`; [`ExecuteOpcodeStream`, `0x6F45E9D0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F45E9D0.json) оставляет продвинутый cursor в `instance+0x20`. [`CTriggerExecution::` обход `0x6F447340`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447340.json) на этом статусе удерживает ключ instance `execution+0x50` и action `+0x54`; timer/callback выпускает `ResumeTriggerExec` с token `+0x90`. Связка сна и callback отдельно разобрана в [FND-0040](FND-0040-jass-vm-yield-status.md) и [FND-0041](FND-0041-trigger-action-continuation.md). Здесь она служит входным условием для последующего эффекта.
2. Обработчик команды [`0x6F440620`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F440620.json) проверяет живой trigger agent и передаёт token в [`0x6F447700`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F447700.json). При равенстве `execution+0x90` функция **сначала увеличивает** это поле, затем вызывает `0x6F447340`; несовпадение token возвращает без обхода. Верхний gate `0x6F447340` при `execution+0x80 != 0` возвращает до action даже после принятия token. Это отрицательные контроли на входе, а не гарантия «ровно один world write». Route-level sender boundary и проверка trigger описаны в [FND-0051](FND-0051-resume-sender-resolution.md) и [FND-0053](FND-0053-trigger-ready-membership-boundary.md).
3. При сохранённом `execution+0x54` обход выбирает тот же action и передаёт флаг начального запуска `arg_14=0` через [`0x6F445800`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F445800.json) → [`0x6F3BA890`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3BA890.json) → [`0x6F3A8340`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3A8340.json) → [`0x6F44B6A0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F44B6A0.json) → [`0x6F45FA30`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F45FA30.json). Последняя функция при ненулевом `instance+0x20` и `arg_14=0` выбирает прежний cursor и вызывает `ExecuteOpcodeStream`; при нулевом cursor либо ненулевом `arg_14` выбирает ветку начального исполнения. Это положительный и отрицательный контроль именно **сохранённого** continuation, без предположения о запуске функции сначала.
4. Если следующий исполняемый bytecode содержит native-call opcode case `21` с ключом `SetUnitState`, `ExecuteOpcodeStream` в `0x6F45EFA9` вызывает [`0x6F45D070`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F45D070.json). Через [`0x6F44EA00`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F44EA00.json) она ищет native record в таблице TLS slot `5` `+0x18`, берёт сигнатуру `record+0x24` и функцию `+0x1C`, собирает аргументы и косвенно вызывает её в `0x6F45D1B5`. [S11 registration `0x6F3D4020`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3D4020.json) и [S10 registration](../../../../src/Jass/jassregisterallnatives.cpp) связывают `SetUnitState` с адресом `0x6F3C5EA0` и сигнатурой `(Hunit;Hunitstate;R)V`. Общий dispatch установлен в [FND-0054](FND-0054-cross-domain-native-dispatch.md); здесь существенен достижимый из него конкретный setter.
5. [`SetUnitState`, `0x6F3C5EA0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3C5EA0.json) отсекает `state>=4`, вызывает [`ResolveUnitHandle`, `0x6F3BDCB0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3BDCB0.json), а при null либо `state<0` возвращает без setter. Resolver берёт таблицу handles через process-global world `dword_6FAB65F4`, проверяет ненулевой `hUnit`, lookup, тип agent (`0x2B61676C`) и отсутствие pending flag `+0x20`; неуспех ведёт к null fallback. [S10 native](../../../../src/Jass/jassnatives_life.cpp) и [S10 resolver](../../../../src/Jass/jassresolveunithandle.cpp) дают имена операциям. Singleton берётся **до** проверки нулевого handle, поэтому отдельная безопасность этого пути при null world не установлена. В указанном теле resolver нет чтения TLS slot `13` или player slot как контекстного фильтра.
6. На валидном unit [`CUnit::SetState`, `0x6F27AF20`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F27AF20.json) для `state=2` вызывает [`SUnitTrackedRef::SetValue`, `0x6F477350`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F477350.json) у `unit+0xB8` (мана). При валидном tracked ref тот доходит до [`SHandleObjectRangeImpl::AddToValue`, `0x6F4A92B0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F4A92B0.json): после подготовки и ограничения значения пишет в `range+0x78` (`0x6F4A9307`) и вызывает уведомление `0x6F4A9230`. [S10 state mapping](../../../../src/Unit/unit_state.cpp), [S10 tracked ref](../../../../src/Unit/unittrackedref_setvalue.cpp) и [S10 range mutation](../../../../src/Unit/rangeaddvalue.cpp) подтверждают названия полей. `state=0` выбирает виртуальный `SetLife` (`vtable+0x124`), который здесь не прослежен до записи; `state=1/3` в `CUnit::SetState` возвращаются без записи. Последние два состояния — отрицательный контроль уже **после** валидного handle.

## Ограничения и отвергнутые гипотезы

S11 — адресный корпус с разными статусами (`0x6F3C5EA0` и `0x6F27AF20` — `EXACT`; `0x6F3BDCB0`, `0x6F477350`, `0x6F4A92B0` — `DIFFERS`; VM и часть trigger пути — `THUNK`/`TODO`). Это чтение `raw_asm` и S10, не собственный byte-match или запуск Game.dll. Адреса относятся только к указанному источнику без подтверждённого fingerprint. Не найден bytecode карты с `SetUnitState` именно после сна; расположение opcode является явным условием вывода. Не проверены успешность доставки resume, точная идентичность OS-thread/TLS на всём пути, валидность tracked ref для произвольного unit, различие старого и записанного значения, а также все другие пути к этому native.

Token отсекает повтор с прежним значением на данном `CTriggerExecution`, но не доказывает глобальную однократность эффекта, защиту от нового разрешённого token или от другого action. Отсутствие player/domain gate в **показанных** функциях не доказывает его отсутствия во всём исходном матче или в будущей архитектуре. `TriggerSyncReady` при нулевой маске тоже вызывает `0x6F447340` ([FND-0042](FND-0042-trigger-sync-barrier.md)), но этот путь не является доказательством того же сохранённого action/cursor или записи unit: здесь проверен sleep/resume маршрут.

## Значение для проекта

При разделении локальных продолжений и авторитетного мира native нельзя классифицировать только по общему VM dispatcher. Для этого конкретного setter граница эффекта находится после resume token, выбора сохранённого action и разрешения handle в глобальной таблице мира. Минимальный проверочный опыт: двухигроковая карта с одним trigger action `TriggerSleepAction` → `SetUnitState(knownUnit, UNIT_STATE_MANA, distinctValue)`, логировать instance/cursor, token, sender, выбранный world/handle, значение `range+0x78` и число вызовов setter до/после resume. Контроли: stale token, `execution+0x80!=0`, недействительный unit handle, `UNIT_STATE_MAX_MANA` и повтор допустимого вызова из **другого** action. Лишь такой опыт сможет установить фактическое число записей и влияние выбранной архитектуры; статическая карточка этого не утверждает.
