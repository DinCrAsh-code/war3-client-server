## Вывод

S11 показывает один адрес process-global указателя `dword_6FAB4F80` для `CGameUI`: конструктор сохраняет туда `this`, accessor `GetGameUI(create, reset)` читает его и при `reset != 0` обнуляет. Камера хранится внутри этого UI в `+0x254`. Конкретный метод игрового мира `0x6F3A2EC0` сначала обращается к уже существующему UI, а затем вызывает `GetGameUI(0,1)` и позднее повторно регистрирует JASS natives. Один caller метода достигается через живой world object из текущего TLS slot 13; другой вызывается непосредственно на world object при его собственном условии `+0x320 != 0`. В самом `GetGameUI`, camera getter и camera natives нет проверки identity EvtContext или world object. Сброс глобального указателя существует, но на проверенном пути следует **операции сброса мира**, а не переключению TLS array при каждом JASS callback.

Это сужает [FND-0054](FND-0054-cross-domain-native-dispatch.md): два EvtContext с разными TLS arrays не получают автоматически разные camera receivers в одном процессе. Статический корпус не показывает штатного одновременного исполнения двух миров в одном процессе, так что конкуренция их камер остаётся сценарием для проверки новой архитектуры, а не наблюдением об оригинальной игре.

## Основание и контроли

1. [`GetGameUI`, `0x6F300710`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F300710.json) сначала сравнивает `dword_6FAB4F80` с нулём. Если там нуль и `create != 0`, он выделяет объект и вызывает [`CGameUI` constructor `0x6F2FE9F0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F2FE9F0.json), который при `0x6F2FECA3` записывает `this` в глобальный указатель. Если `create == 0`, null сохраняется. Accessor возвращает старое/созданное значение, затем при `reset != 0` записывает в глобальный указатель нуль. Он не читает TLS и не получает identity игрока или world object. [S10 объявление](../../../../src/GameUI/gameui.h) называет оба параметра `create` и `reset`.
2. Конструктор передаёт адрес `ui+0x254` в [`SCheckedCameraSlot::Assign`, `0x6F2F49E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F2F49E0.json), который заменяет ссылку с учётом проверки и счётчика ссылок. [`CGameUI::GetCamera`, `0x6F2F5ED0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F2F5ED0.json) возвращает это поле. [`CGameUI` destructor `0x6F300220`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F300220.json) при ненулевом `+0x254` уменьшает счётчик ссылки и вызывает release при нуле; сам деструктор **не** обнуляет `dword_6FAB4F80`. Это положительный контроль, что camera привязана к объекту UI, а обнуление глобального имени — отдельное действие. Тело [S10 camera getter](../../../../src/GameUI/gameuigetcamera.cpp) подтверждает layout.
3. В [`0x6F3A2EC0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3A2EC0.json), где `ecx` — world receiver, вызов `GetGameUI(0,0)` при `0x6F3A304E` получает существующий UI. При null пропускается UI-specific блок; при ненулевом указателе вызывается его vtable slot `+0xD8` с аргументом `1`. [S11 CGameUI vtable `0x6F93631C`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/classes/0x6F93631C.json) разрешает этот slot в [`0x6F606910`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F606910.json): метод базового `CFrame` освобождает и обнуляет свой ресурс `+0x160`. У той же vtable отдельный slot `+0x04` указывает на [`0x6F300840`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F300840.json), вызывающий `CGameUI` destructor `0x6F300220`. Значит, показанный `+0xD8` вызов — **не** удаляющий деструктор UI. **В обоих случаях** при `0x6F3A308D` выполняется `GetGameUI(0,1)`, обнуляющий global pointer. После других операций тот же метод вызывает регистрацию JASS natives `0x6F3D4020` при `0x6F3A313E`. Null UI — отрицательный контроль для виртуального вызова, но не для сброса глобального указателя.
4. [`0x6F3A3AD0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3A3AD0.json) берёт TLS slot `13` через `0x6F4C34D0`, затем `slot13+0x10→+0x18`. Только при ненулевом world pointer вызывает `0x6F3A2EC0`; далее вызывает world vtable slot `+0x08` с аргументом `1`, записывает нуль в `+0x18` и в global `dword_6FAB65F4`. Это положительный контроль привязки **одного caller** к текущему TLS13 world и отрицательный контроль: null world пропускает `0x6F3A2EC0` на этом пути. При этом другой caller, [`0x6F3A49E0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3A49E0.json), вызывает `0x6F3A2EC0` прямо на своём `world` при `world+0x320 != 0`; при нуле уходит за ветвь. Значит, нельзя приписать сброс UI исключительно TLS13 cleanup.
5. [`GetLocalPlayer`, `0x6F3BBB60`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3BBB60.json) тоже использует глобальный world pointer, но его выбор player slot дополнительно зависит от текущего TLS13 ([FND-0049](FND-0049-local-player-slot-writers.md)). [`GetCameraField`, `0x6F3B4CD0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3B4CD0.json) и [`SetCameraField`, `0x6F3B48B0`](https://github.com/FilippTheBestDev/claudecraft/blob/10950d496aa7357a6180c1956def50c2a3e8c1a9/agent_worktrees/funcs/0x6F3B48B0.json) вызывают `GetGameUI(1,0)` и идут через `CGameUI::GetCamera`, без TLS13/player-slot выбора в показанных телах. Это контроль различия локальной идентичности и camera receiver при одинаковом общем native dispatch. [FND-0048](FND-0048-event-context-tls-rebinding.md) отдельно фиксирует, когда worker привязывает TLS array EvtContext.

## Ограничения и отвергнутые гипотезы

Непосредственные ссылки на `dword_6FAB4F80` и прямые вызовы `GetGameUI` в S11 не исключают косвенных alias writes, virtual calls или других путей смены UI. Показанный `reset` **не освобождает объект сам по себе**, а virtual `+0xD8` чистит ресурс базового `CFrame`; дальнейший lifetime всего `CGameUI` и его камеры по этому пути не установлен. Вызов `0x6F3A2EC0` при сбросе/переинициализации мира не доказывает, что он происходит между двумя конкретными JASS callbacks или что в оригинале одновременно существуют два мира. Статусы записей S11 включают `THUNK`, `TODO`, `EXACT` и `IDENTICAL`; это чтение адресного корпуса, без byte verification или собственного запуска DLL. Не утверждается, что отдельный UI на каждого игрока нужен именно как копия всего оригинального `CGameUI`: достаточно будет проверяемого разделения local presentation receiver в целевой модели.

## Значение для проекта

При проверке варианта с несколькими EvtContexts в одном серверном процессе нужно наблюдать не только TLS slots `5/13` и `GetLocalPlayer`, но и адреса `dword_6FAB4F80`, `ui+0x254` и момент `GetGameUI(0,1)` относительно каждого world lifecycle. Минимальный опыт: два разных контекста последовательно вызывают camera natives; сравнить receiver UI/camera до и после `0x6F3A2EC0`, отдельно пройти null world и `world+0x320==0`. Только такой опыт покажет, даёт ли выбранная схема независимые локальные эффекты и удерживает ли камера корректный lifetime при сбросе мира.
